## 2. Detailed Technical Solutions

### 2.1 Issue 1: Mobile UI Overhaul & Overflow Prevention
#### Problems Identified:
1. **Vertical Button Stretching**: `.mode-card` currently has `padding: 32px 28px;`, large 64px icon containers, multi-line paragraph descriptions, and action rows that push content off the screen on phones.
2. **Horizontal Overflow**: Padding accumulation (`padding: 32px 40px` on viewport + `36px 32px` on dashboard = 144px consumed by padding alone) causes horizontal scrolling on 360–412px mobile screens. Long file paths and metrics tables wrap incorrectly.

#### Solutions:
- **Compact Mobile Mode Cards**:
  - Replace the heavy cards with sleek, compact action buttons on screens `< 650px`.
  - Remove verbose descriptive paragraphs on mobile viewports; show only high-contrast, bold **`Send`** and **`Receive`** action titles with icons.
- **Viewport & Padding Scaling**:
  - Add responsive CSS `@media (max-width: 650px)` breakpoint:
    - Viewport padding reduced to `14px 12px`.
    - Dashboard padding reduced to `16px 12px`.
    - Body set to `overflow-x: hidden; width: 100vw; max-width: 100vw;`.
  - Metrics row (`.metrics-row`) switched from rigid 3-column grid to responsive 2-column or flex wrap.
  - Path and file displays set to `word-break: break-all; text-overflow: ellipsis; white-space: nowrap; overflow: hidden;`.

### 2.2 Issue 2: Transfer Cancellation & State Machine Reset
#### Problems Identified:
- When a transfer is cancelled (`btnCancelTransfer`), the app returns to `viewHome`, but:
  1. The socket reader or stream does not immediately flush in the background.
  2. The UI progress bar width, byte counter, speed telemetry, and file index retain their old values.
  3. Starting a new transfer immediately triggers lingering telemetry callbacks from the previous session, causing UI freeze.

#### Solutions:
- **Centralized State Reset Engine (`resetTransferState()`)**:
  - Reset all telemetry indicators: `progressBarFill` &rarr; `0%`, `metricSpeed` &rarr; `0.0 MB/s`, `metricEta` &rarr; `--`, `currentFileNameText` &rarr; `""`.
  - Clear staged files and session variables.
  - Generate a new unique `sessionId` (e.g. `UUID.randomUUID()`) for each transfer attempt. Telemetry events with stale `sessionId` are discarded immediately.
- **Native Teardown**:
  - Android: `transferClient.cancel()` cleanly disconnects `HttpURLConnection` and closes open streams.
  - Windows: `TransferClient.Cancel()` invokes `CancellationTokenSource.Cancel()` and immediately disposes the active `StreamContent`.

### 2.3 Issue 3: Android &rarr; Windows Transfer Stalled on "Initializing"
#### Root Causes Identified:
1. **HTTP `Expect: 100-continue` Deadlock**:
   - In Android Java, `HttpURLConnection` with `setFixedLengthStreamingMode()` automatically sends the HTTP header `Expect: 100-continue`.
   - The Windows `TransferServer.cs` (`TcpListener`) currently parses headers but does **not** send the interim `HTTP/1.1 100 Continue\r\n\r\n` response.
   - Consequently, Android pauses and waits indefinitely for the 100-continue response, stalling on "Initializing transfer".
2. **Virtual Network Adapter IP Mismatch**:
   - On Windows PCs with Hyper-V, WSL2, or VMware/VirtualBox, `DiscoveryService.GetLocalIpAddress()` may report a virtual adapter IP (e.g., `192.168.56.1` or `172.x.x.x`) instead of the true Wi-Fi LAN IP (e.g., `192.168.1.x`).
   - Android tries to connect to the unreachable virtual IP.

#### Solutions:
- **Expect Header Fix**:
  - In Android [TransferClient.java](file:///c:/Users/wwdin/Desktop/EzShare/android/app/src/main/java/com/ezshare/app/TransferClient.java): explicitly set `conn.setRequestProperty("Expect", "");` to disable 100-continue negotiation.
  - In Windows [TransferServer.cs](file:///c:/Users/wwdin/Desktop/EzShare/Services/TransferServer.cs): check incoming headers; if `Expect: 100-continue` is present, immediately flush `HTTP/1.1 100 Continue\r\n\r\n`.
- **IP Detection Enhancement**:
  - In Android discovery handler: If the device IP reported in the JSON packet differs from the actual UDP sender IP `packet.getAddress().getHostAddress()`, prefer the actual incoming socket address.
  - In Windows discovery service: Filter out virtual adapters (`vEthernet`, `VirtualBox`, `VMware`, `WSL`) and prioritize active Wi-Fi/Ethernet adapters with default gateways.

### 2.4 Issue 4: Persistent Default Receive Folder
#### Requirement:
Remember the last chosen destination directory on both Windows and Android so the user does not have to browse and pick a folder every time, while still offering a `[ Change Folder ]` option.

#### Implementation:
- **Android**:
  - Use `SharedPreferences`:
    ```java
    // Save
    prefs.edit().putString("default_receive_uri", folderUri.toString()).apply();
    
    // Retrieve & validate
    String savedUriStr = prefs.getString("default_receive_uri", null);
    if (savedUriStr != null) {
        Uri savedUri = Uri.parse(savedUriStr);
        // Verify persistable permission is still granted
        if (hasPersistablePermission(savedUri) && DocumentFile.fromTreeUri(context, savedUri).canWrite()) {
            selectedFolderUri = savedUri;
        }
    }
    ```
  - When the user selects "Receive", if a valid saved folder exists, jump directly to the "Ready to Receive" beacon screen using that folder.
- **Windows**:
  - Store default folder in local app settings / `%LOCALAPPDATA%\EzShare\config.json`.
  - Default initial path: `Environment.GetFolderPath(SpecialFolder.UserProfile) + "\Downloads\EzShare"`.
  - Auto-create the directory if it does not exist, and allow one-click changing.

### 2.5 Issue 5: Android Downloads Folder & All Files Access (`MANAGE_EXTERNAL_STORAGE`)
#### Problem Identified:
On Android 11+ (API 30+), Google's Storage Access Framework (SAF) deliberately blocks selecting the root `Downloads`, `Android/data`, and `Android/obb` folders in `ACTION_OPEN_DOCUMENT_TREE` ("Can't use this folder" OS dialog).

#### Solution:
Provide high-privilege All-Files Access with graceful fallback:
1. **Manifest Declaration**:
   ```xml
   <uses-permission android:name="android.permission.MANAGE_EXTERNAL_STORAGE" tools:ignore="ScopedStorage" />
   ```
2. **Runtime Check & Permission Flow**:
   - Check if `Environment.isExternalStorageManager()` returns `true`:
     - **If Granted**: App streams directly to `Environment.getExternalStoragePublicDirectory(Environment.DIRECTORY_DOWNLOADS) + "/EzShare"` using standard Java `File` and `FileOutputStream` (bypassing slow SAF and allowing direct Downloads storage!).
     - **If Not Granted**:
       - Present a clean, friendly modal: *"To save directly into your Downloads folder without manual folder picking, enable All Files Access."*
       - Button &rarr; `startActivity(new Intent(Settings.ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION, Uri.parse("package:" + getPackageName())))`.
       - Fallback: User can still pick any custom subfolder via SAF if they decline.
